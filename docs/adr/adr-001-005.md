# ADR-001：规则引擎采用混合模式（前端即时 + 后端推理）

**编号**：ADR-001
**状态**：✅ 已接受（2026-10-07 内部计划文档 拍板，2026-10-12 落地细则收编）
**背景**：规则引擎需要在"浏览器内即时反馈"（用户勾选 Profile 字段时立刻看到因素激活）与"复杂推理可审计"（DEP/MOD/CNF 多跳链路 + 审计日志）之间取舍。

## 决策

- **前端**（MVP）：ACT 9 条激活规则即时执行；条件表达式用安全子集解释器（`==`/`>`/`<`/布尔），无 eval；规则数据从 data-pack 加载（数据驱动，更新不改动代码）
- **后端**（v2+，Supabase Edge Functions）：DEP/MOD/CNF 推理链 + 审计日志 + 边界文档云存证
- **共用契约**：`RuleEngine.evaluate(profile): Recommendation` 接口前后端一致，实现可替换；规则 schema 同源（rules.yaml → 构建期生成两份产物：前端 TS 数据 + 后端 SQL 种子）

## 理由

- ACT 规则条件简单（单字段判断），浏览器执行延迟 <10ms，无需网络
- DEP/MOD 规则跨因素引用（如 DEP-001 依赖认知负荷水平），推理需要完整 Profile 状态与执行顺序保证，适合服务端
- 混合模式避免 MVP 背后端包袱（ADR-002），又不在架构上堵死后路

## 后果

- 正面：MVP 零后端成本；推荐响应即时；v2 演进路径清晰
- 负面：MVP 内 CNF 冲突仅文本提示不做推理（产品需求文档 F3 诚实标注）；两份产物需要构建脚本维护一致性
- 缓解：规则产物由同一 yaml 生成（单一事实源），CI 校验两份产物 hash 一致

# ADR-002：MVP 单用户 + IndexedDB 本地存储，无账号无后端

**编号**：ADR-002
**状态**：✅ 已接受（2026-10-07 内部计划文档 拍板，2026-10-12 落地细则收编）

## 决策

MVP 无账号体系、无多租户、无后端。用户数据（项目 Profile / 边界文档 / 审计状态）存浏览器 IndexedDB（Dexie 封装），提供**单一 JSON 全量导入导出**。边界文档 JSON 从 Day 1 定义为 v1 稳定契约（additive-only 演进）。

## 理由

- 目标用户（P1/P2 画像）对"上传设计任务到第三方服务器"有真实隐私顾虑（WHO-F-014 因素的自举应用）
- 单用户模式砍掉 Auth/数据库/合规三座大山，MVP 工期集中在四阶段核心流程
- 边界文档作为稳定契约先行：v2 加同步层时旧数据直接可迁，避免格式返工
- 开源工具的信任策略：本地优先是包容性设计工具应有的姿态（工具自身实践它倡导的原则）

## 后果

- 正面：部署降为纯静态托管；隐私即卖点；离线可用（弱网/内网场景友好——HOW-F-001 自举）
- 负面：换设备/浏览器数据不互通（v1 用户需手动导出导入）；无团队协作
- 缓解：导出文件设计为人类可读 JSON（工具不锁死数据）；v2 同步层按边界文档契约平滑接入

# ADR-003：中英双语基础设施（zh-CN 优先）

**编号**：ADR-003
**状态**：✅ 已接受（2026-10-07 内部计划文档 拍板，2026-10-12 落地细则收编）

## 决策

- 数据层：全部知识卡片 front-matter 双字段（`name`/`name_en`），数据包双语齐发
- UI 层：vue-i18n 资源文件，zh-CN 为源语言（完整度 100%），en 为翻译目标
- 术语：维护中英术语对照表（wiki 公开页），作为翻译基准与低门槛贡献入口
- 知识卡正文：MVP 中文发布 + 标题双语；正文英译走 W4 长期社区轨道

## 理由

- 用户主体在中文语境（GB/GB-T 标准挂接是本项目独有资产，中文受众价值最高）
- 国际开源需要英文（GitHub 生态、WCAG/W3C 社区引用回流）
- front-matter 双字段在 155 张卡已全量存在（本 ADR 收编的是既成事实的标准化）

## 后果

- UI 文案双份维护成本；英文术语表翻译质量依赖社区审校
- 缓解：i18n 缺失键 CI 检查（en 落后 zh-CN 时构建警告不失败）

# ADR-004：wiki 发布选型 Quartz（v5，替代内部研究档案原定 MkDocs Material）

**编号**：ADR-004
**状态**：✅ 已接受（2026-10-12 新增；2026-10-12 PoC 后勘误版本号）
**背景**：早期规划 原候选为 MkDocs Material；内部计划文档 阶段记为 Quartz 4；PoC 实测拉取 master 已是 **Quartz 5**（配置制 yaml + 插件生态）。决策依据经 PoC 实测验证（INCL-POC-001）。

## 决策

知识库 wiki 发布采用 **Quartz（v5）**：vault（Obsidian 风格 Markdown + 双链 + front-matter）直接作为 Quartz content 目录，`npx quartz build` 产出纯静态站托管 GitHub Pages。PoC 实测：227 卡 0 丢弃、546 文件产出、双链原生渲染、内容索引 246 条。

## 理由

| 维度 | Quartz 4 | MkDocs Material |
|------|----------|----------------|
| Obsidian 双链 `[[...]]` | 原生渲染（含呼出/别名/反链面板） | 需插件且效果受限 |
| front-matter 丰富字段 | 原生容忍 + 可映射为页面属性 | 部分支持 |
| 图谱/关系可视化 | 内置（因素↔指标↔指南↔案例的关系网是知识库核心价值） | 无 |
| 部署 | 纯静态，Pages 零成本 | 纯静态，同等 |
| 中文搜索 | FlexSearch CJK 分词弱（风险） | 内置中文搜索较好 |

- 决定性因素：**双链与图谱**。155 张卡的关系网（240 条链接）是研究资产的核心结构价值，Quartz 把它变成可导航体验；MkDocs 的线性 nav 结构会把知识库降维成目录树
- 中文搜索风险有明确回退（架构文档 §3.1：字母索引 + 维度目录树导航），且 227 卡规模下导航检索压力可控

## 后果

- 搜索体验若最终不可用，MVP 接受降级方案；v1.1 再评估 CJK 适配插件
- 团队需维护 Quartz 配置（npm 依赖更新）；换来的是知识库视觉/交互与工具品牌一致

# ADR-005：数据包构建期生成 + 内容 hash 版本化（yaml 单源 → 前端只读数据）

**编号**：ADR-005
**状态**：✅ 已接受（2026-10-12，本文档新增）
**背景**：前端如何消费 4 注册表 yaml + 227 张卡片：运行时解析 yaml？构建期转 JSON？还是 API 动态服务？

## 决策

**构建期**把 `registry/*.yaml` 解析为单一 `data-pack-<hash>.json`：
1. CI 先跑 `schema/validate.py`（全绿门禁），失败即中断
2. `scripts/build-data.mjs` 生成数据包：factors/metrics/rules/standards 全量 + guides/cases 摘要（模式名/反模式名，全文跳 wiki）
3. 文件名含内容 hash；SPA 启动时比对 hash 决定是否重新拉取
4. 应用运行时**只读**数据包，永不回写 yaml

## 理由

- 运行时解析 yaml 需要 js-yaml + 1.5MB 文本传输 + 解析开销；构建期一次转换，浏览器只拿精炼 JSON（预估 <800KB gzip）
- "知识即数据"（内部研究档案 §3.4）的工程化落点：yaml 是贡献者界面，JSON 是应用界面，schema 是两者间的合同
- hash 版本化让知识库热更新（研究资产迭代）与应用发版解耦：新数据包上线，旧 SPA 自动取新
- 校验门禁前置到构建：研究资产的 165 文件完整性约束直接传导到产物层（错误的知识进不了应用）

## 后果

- 正面：前端零解析负担；知识更新到用户的链路是"push tag → CI → 新 hash 文件"全自动
- 负面：build-data.mjs 需与 schema 演进同步维护（schema 加字段 → 脚本同步）；数据包需做 gzip（Pages 原生支持）
- 缓解：build-data.mjs 内嵌 schema 字段清单常量，CI 中比对 schema 文件变化提醒同步
