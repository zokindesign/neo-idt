## 一、规则引擎概述

### 1.1 设计动机

因素体系包含七个维度下的 54 个因素 + 7 个合规基线，各因素之间存在复杂的相互影响关系。例如：

- “网络条件”在“在线视频会议”任务下成为关键约束，但在“本地文档阅读”任务下几乎无关
- “视觉风格偏好”可能受到“光线条件”环境的调节（强光下偏好高对比度）
- “认知负荷”与“引导程度偏好”之间存在补偿关系（高负荷 → 需要更多引导）

规则引擎旨在**系统性地描述这些关系**，为设计决策提供可操作的推理规则。

### 1.2 规则引擎架构

```
┌───────────────────────────────────────────────────────────────┐
│                    因素关系规则引擎                              │
├───────────────────────────────────────────────────────────────┤
│                                                               │
│  规则类型层（定义于 registry/rules.yaml）                      │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐        │
│  │ 激活规则  │ │ 依赖规则  │ │ 调节规则  │ │ 冲突规则  │        │
│  │ ACTIVATE │ │ DEPEND   │ │ MODERATE │ │ CONFLICT │        │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘        │
│  ┌──────────┐                                                │
│  │ 补偿规则  │                                                │
│  │ COMPENSATE│                                               │
│  └──────────┘                                                │
│                                                               │
│  规则推断引擎                                                  │
│  输入：任务情境 + 用户画像 + 环境条件 + 商业约束               │
│  输出：活跃因素列表 + 因素优先级排序 + 冲突裁决 + 补偿方案      │
│                                                               │
└───────────────────────────────────────────────────────────────┘
```

### 1.3 核心原则：ID 化引用

**所有规则引用因素一律使用 `registry/factors.yaml` 中的标准 ID**（如 `WHO-F-001`、`HOW-F-002`），**废除**“维 N”“维度三”等序号式引用——序号引用会随维度调整而失效，是 v2.0 版本翻车的根源。

## 二、五类规则类型详解

### 2.1 激活规则 —— 条件性激活

**定义**：因素 A 仅在条件 C 满足时才成为有效约束。

**格式**：
```yaml
- id: ACT-001
  type: activate
  condition: "task.category == 'online-communication'"
  activates: [HOW-F-001]  # 网络条件
```

**完整清单**（9 条，详见 `rules.yaml`）：

| 规则 ID | 条件 | 被激活因素 | 说明 |
|---------|------|------------|------|
| ACT-001 | 任务类型 = 在线通信 | HOW-F-001 (网络条件) | 离线任务下网络不构成约束 |
| ACT-002 | 交互形式 = 语音输入 | WHO-F-001 (身体能力/听觉) | 纯文本交互听觉非必要 |
| ACT-003 | 设备 = 移动端 | WHO-F-001 (身体能力/运动) | 桌面端不涉及握持/移动 |
| ACT-004 | 使用场景 = 公共场合 | WHICH-F-007 (反馈偏好/音频) | 私密场景音频非约束 |
| ACT-005 | 包含多人协作 | WHICH-F-004, WHAT-F-005 | 单人任务社交因素不激活 |
| ACT-006 | 任务类型 = 数据录入 | WHAT-F-003 (容错性) | 录入任务需要强撤销支持 |
| ACT-007 | 任务步骤数 > 10 | WHAT-F-001, WHAT-F-002 | 长流程任务自动激活高负荷 |
| ACT-008 | 截止时间 < 预估×1.2 | WHEN-F-004 (时间压力) | 时间紧张触发压力感知 |
| ACT-009 | 包含支付/确认环节 | WHAT-F-003 (增强容错性) | 金融操作需要强确认 |

---

### 2.2 依赖规则 —— 因素间的依赖性

**定义**：因素 A 的有效性依赖于因素 B 的状态。

**格式**：
```yaml
- id: DEP-001
  type: depend
  dependent: WHICH-F-003  # 控制感偏好/引导程度
  dependency: WHAT-F-002  # 认知负荷
  condition: "WHAT-F-002.level == 'high'"
```

**完整清单**（7 条）：

| 规则 ID | 依赖方 A | 被依赖方 B | 条件 | 说明 |
|---------|----------|------------|------|------|
| DEP-001 | WHICH-F-003 (引导程度) | WHAT-F-002 (认知负荷) | 高负荷时 | 复杂任务下引导需求上升 |
| DEP-002 | WHICH-F-005 (视觉风格) | WHERE-F-001 (物理环境) | 强光环境 | 环境光线制约视觉呈现选择 |
| DEP-003 | WHICH-F-001 (信息密度) | HOW-F-002 (设备能力) | 小屏幕 | 屏幕限制信息呈现空间 |
| DEP-004 | WHICH-F-003 (控制感) | WHO-F-007 (技术素养) | 新手 | 新手对自动化接受度更高 |
| DEP-005 | WHY-F-001 (商业可行性) | RUL-001 (法规合规) | 始终 | 政策合规是商业可行的前提 |
| DEP-006 | WHICH-F-003 (自动化程度) | WHAT-F-004 (任务持久性) | 高重复性 | 重复任务用户更倾向自动化 |
| DEP-007 | WHICH-F-007 (反馈密度) | WHEN-F-004 (时间压力) | 高时间压力 | 时间紧时偏好总结反馈 |

---

### 2.3 调节规则 —— 因素的调节效应

**定义**：因素 A 的状态会放大或减弱因素 B 的影响强度。

**格式**：
```yaml
- id: MOD-001
  type: moderate
  moderator: WHEN-F-004  # 时间压力
  target: WHICH-F-001  # 信息密度偏好
  direction: amplify
```

**完整清单**（7 条）：

| 规则 ID | 调节因素 A | 被调节因素 B | 方向 | 说明 |
|---------|------------|--------------|------|------|
| MOD-001 | WHEN-F-004 (时间压力) | WHICH-F-001 (简洁度) | +放大 | 时间紧时更倾向简洁 |
| MOD-002 | WHICH-F-004 (社交压力) | WHO-F-014 (隐私偏好) | +放大 | 社交压力大时更注重隐私 |
| MOD-003 | WHO-F-006 (感官偏好) | WHICH-F-001 (信息密度) | +放大 | 听觉学习者需要更高信息密度 |
| MOD-004 | WHO-F-001 (生理节律) | WHICH-F-007 (响应速度) | −减弱 | 疲劳时段容忍度更高 |
| MOD-005 | WHICH-F-008 (创新偏好) | WHICH-F-003 (控制感) | −减弱 | 创新偏好者更接受自动化 |
| MOD-006 | WHAT-F-001 (复杂度) | WHICH-F-003 (引导需求) | +放大 | 复杂任务需要更多引导 |
| MOD-007 | WHAT-F-003 (容错性) | WHICH-F-007 (确认强度) | +放大 | 低容错要求强确认 |

---

### 2.4 冲突规则 —— 因素间的权衡

**定义**：因素 A 与因素 B 的最优方案存在冲突，需要折中。

**格式**：
```yaml
- id: CNF-001
  type: conflict
  factor_a: WHO-F-014  # 隐私偏好
  factor_b: WHICH-F-001  # 个性化推荐
  priority_rule: "privacy_first"
```

**完整清单**（7 条）：

| 规则 ID | 冲突方 A | 冲突方 B | 优先级规则 | 说明 |
|---------|----------|----------|------------|------|
| CNF-001 | WHO-F-014 (隐私) | WHICH-F-001 (个性化) | privacy_first | 个性化与隐私的矛盾 |
| CNF-002 | WHY-F-001 (成本) | WHICH-F-005 (感官丰富度) | core_function_first | 预算限制感官设计 |
| CNF-003 | RUL-001 (法规合规) | WHICH-F-005 (视觉风格自由) | compliance_over_freedom | 无障碍标准限制设计自由 |
| CNF-004 | WHICH-F-008 (创新) | WHICH-F-005 (经典一致性) | new_user_priority | 老用户稳定 vs 新用户创新 |
| CNF-005 | HOW-F-002 (设备能力) | WHICH-F-005 (动效密度) | function_over_experience | 性能不足时降级动效 |
| CNF-006 | WHEN-F-004 (时间压力) | WHAT-F-003 (容错性) | risk_level_priority | 时间紧 vs 准确性权衡 |
| CNF-007 | WHAT-F-001 (复杂度) | WHICH-F-003 (控制感) | novice_simple_first | 新手面对复杂任务，简化优先 |

---

### 2.5 补偿规则 —— 因素间的替代补偿

**定义**：当因素 A 无法满足时，可通过优化因素 B 来补偿。

**格式**：
```yaml
- id: CMP-001
  type: compensate
  unavailable: WHO-F-001  # 视觉能力
  compensates: [WHO-F-006, WHICH-F-006]  # 感官偏好、输入方式
```

**完整清单**（4 条）：

| 规则 ID | 不可用因素 A | 补偿因素 B | 说明 |
|---------|--------------|------------|------|
| CMP-001 | WHO-F-001 (视觉能力) | WHO-F-006, WHICH-F-006 | 视觉障碍 → 听觉/触觉补偿 |
| CMP-002 | HOW-F-001 (网络条件) | HOW-F-003, HOW-F-005 | 连接不良 → 离线/低带宽模式 |
| CMP-003 | WHEN-F-005 (时间可用性) | WHAT-F-001, WHICH-F-003 | 时间压力 → 预设模板/快速路径 |
| CMP-004 | HOW-F-002 (设备能力) | WHICH-F-005, WHICH-F-008 | 性能弱 → 简化界面/减少动效 |

## 三、规则综合应用示例

### 示例 1：在线视频会议工具设计

```
情境：
  - 任务类型 = "在线通信"          → ACT-001 激活 HOW-F-001 (网络条件)
  - 任务包含多人互动              → ACT-005 激活 WHICH-F-004 (社交可见性)、WHAT-F-005 (协作性)
  - 用户处于强光环境              → DEP-002: WHICH-F-005 (视觉风格) 依赖 WHERE-F-001 (光线)
  - 时间紧张                      → MOD-001: 放大 WHICH-F-001 (简洁度需求)
  - 网络差 + 高清晰度需求         → CNF-005: 优先功能性 → 降级视频质量

综合推断结果：
  1. 首要约束：HOW-F-001 (网络条件) → 自适应画质
  2. 用户调节：WHEN-F-004 (时间压力) → 简化会议室 UI
  3. 冲突处理：WHO-F-014 (隐私) vs WHICH-F-001 (互动) → 默认隐身加入
  4. 环境补偿：WHERE-F-001 (强光) → 高对比度 UI 自适应
```

### 示例 2：移动端购物应用设计

```
情境：
  - 设备 = "移动端"               → ACT-003 激活 WHO-F-001 (运动能力/单手操作)
  - 小屏幕                        → DEP-003: WHICH-F-001 (信息密度) 受 HOW-F-002 限制
  - 新用户                        → DEP-004: WHICH-F-003 (控制感) 新手更接受引导
  - 高认知负荷 + 引导需求         → DEP-001: 强化引导

综合推断结果：
  1. 首要约束：HOW-F-002 (屏幕尺寸) → 信息分层呈现
  2. 用户状态：WHO-F-007 (新手) → 提供购物向导
  3. 认知辅助：WHAT-F-002 (高负荷) → 智能推荐
  4. 运动优化：WHO-F-001 (单手操作) → 底部导航栏
```

## 四、规则引擎推理流程

### 4.1 输入参数

| 参数 | 说明 | 示例 |
|------|------|------|
| **任务情境** | 描述任务类型、使用场景 | "在线视频会议/移动端" |
| **用户画像** | 用户能力 & 偏好概况 | "新手/视觉型/高隐私偏好" |
| **环境条件** | 物理 + 技术环境参数 | "强光/公共场合/低带宽" |
| **商业约束** | 成本 / 市场限制 | "低预算/快速迭代" |

### 4.2 推理步骤

```
第1步：激活规则扫描 (ACT)
  → 任务情境激活对应因素
  → 标注所有"活跃因素"

第2步：依赖规则扫描 (DEP)
  → 确定因素间依赖关系
  → 标注"受限因素"

第3步：调节规则扫描 (MOD)
  → 识别调节效应
  → 调整因素影响权重

第4步：冲突规则扫描 (CNF)
  → 识别冲突因素对
  → 应用优先级规则折中

第5步：补偿规则扫描 (CMP)
  → 识别无法满足的因素
  → 生成补偿方案
```

### 4.3 输出产物

| 输出项目 | 说明 | 用途 |
|----------|------|------|
| **活跃因素列表** | 当前情境下有效的因素 | 设计输入 |
| **因素优先级排序** | 按影响力和紧急度排序 | 资源分配 |
| **冲突因素对** | 需要折中的因素组合 | 设计决策 |
| **补偿方案** | 无法满足时的替代方案 | 兜底策略 |
| **边界文档** | 因素×指标×档位承诺清单 | 审计基准 |
